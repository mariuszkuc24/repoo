In-memory User Guard

An Express.js heartbeat crafted for prototyping — health telemetry, JSON middleware, complete CRUD control, and graceful errors bundled behind a single shimmering endpoint.

Architecture at a glance

  • Express handles every request, logging startup on process.env.PORT || 3000.
  • The JSON parser middleware is global — every route consumes structured payloads instantly.
  • Users are held in-memory: IDs 1 (John) and 2 (Jane) with nextUserId primed at 3.

Endpoint pillars

GET /health

Returns { status: 'OK', timestamp, uptime } so load balancers and monitors can trust the service is alive.

GET /users & /users/:id

Offers the full roster plus guarded detail lookups that respond 404 when the ID disappears from the array.

Mutations

POST, PUT, and DELETE wield validation and messaging to keep data tidy before returning the updated or removed user.

Middleware & store

app.use(express.json()) stands guard before any route code executes.

A mutable users array seeds John (ID 1) and Jane (ID 2) so the service is query-able immediately.

nextUserId auto-increments starting at 3, keeping IDs consistent across creates.

Error & export pathways

  • Custom middleware logs err.stack and responds with 500 + env-aware message.
  • Every missing endpoint flows to a 404 handler with { error: 'Endpoint not found' }.
  • module.exports = app keeps the stack test-friendly and sharable.
"Consistency in error shape makes observability and integration tests effortless."

Validation defense grid

Payload gate

POST cannot run unless name and email arrive together. Missing fields trigger 400 + echo.

Email syntax

Simple yet effective: !email.includes('@') maps to a 400 response so only valid addresses persist.

Partial updates

PUT enforces at least one of name or email; the user object only mutates when new data arrives.
